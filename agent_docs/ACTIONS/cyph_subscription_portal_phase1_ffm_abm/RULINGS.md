## R-012 — REPAIR_002: pending checkout must respect current prerequisites; count-driven work bounded (QA Lead dispatch, R-010 route)
- **ID / date / seat:** R-012 · 29 October 2026 (Asia/Dhaka) · recorded by Claudy (Engineer). Repair authorized by JARVIS (QA Lead) under the existing R-010 repair route; no business decision is made here.
- **Approving source:** QA Lead dispatch, 29 Oct 2026: "Gate Q FAIL for this candidate. CR-F01 blocks acceptance. CR-F02 requires a bounded robustness repair." … "A pending registration must not advance to paid/confirmed activation when the required owner declaration is no longer explicitly true. Enforce this in the mock service and UI. Hiding a button alone does not satisfy the repair." … "Do not reintroduce the unapproved 20-store business cap or silently substitute another arbitrary purchasing limit."
- **Base:** `qa/ffm-abm-001-subscription-portal` @ `24cf075dc3c6252bc22712b067cbf9a8680f24fa` (Director commit of AMENDMENT_001).
- **Repair semantics (frontend / mock service only):**
  1. *Open checkout* = an unpaid checkout nobody has submitted payment on: status `pending` with no activation waiting, or `declined` (Stripe kept the visitor). *Submitted* = `pending` with activation `paymentState: pending` ("processing") or `unknown`. *Completed history* = `paid` / payment `confirmed`.
  2. **Pending invalidation.** Withdrawing the owner declaration (owner step Continue or Back), restoring a storage-v1 draft, or any material draft change (store count, pharmacy details, code — the existing `touch`) **closes** an open checkout: status `abandoned`, new internal field `CheckoutRecord.closedReason` (`owner_declaration` | `details_changed`), quote dropped, consents cleared, draft details kept. Nothing is charged; the record is kept, not erased.
  3. **Current-prerequisite gate.** Every move of an unpaid checkout toward payment re-checks the draft as it is now (`checkoutHold`: declaration exactly `true`, then `isDraftComplete`): same-key `startCheckout` replay, `resolveCheckout('paid' | 'processing')`, `resolveUnknownPayment('paid')`, and `refreshActivation` pending→confirmed. A failure returns `missing_context` and leaves state unchanged. Non-advancing outcomes (back, decline, unknown, nothing-charged, the payment-failed plan) stay available. A submitted payment is **held, not closed**: it can confirm once the owner explicitly accepts again.
  4. **No silent restoration.** Re-accepting does not reopen a closed checkout or restore consent. The path is owner declaration → review ("Get a fresh quote") → fresh consent → a new checkout. Acceptance is never inferred from payment, email, store-admin nomination or an old checkout; storage-v1 drafts never carry acceptance over (forced `false`).
  5. **Completed history is untouched:** a later draft edit never closes, reverses or rewrites a `paid` checkout or confirmed activation.
  6. **CR-F02 — bounded work.** `setStoreCount` no longer creates one placeholder per requested store; pharmacy entries are created only as each step is filled in. Steps fill in order (`isPharmacyStep`: valid count, index < count, index ≤ entries), so a far index can't create a count-sized sparse array. Work and storage scale with entered pharmacies, never the requested count. No business cap is added; the only bound remains the technical safe-integer pricing bound (`MAX_REPRESENTABLE_STORES`, R-010/REPAIR_001).
  7. **R2-N02 (self-found).** The pharmacy route accepted at most a two-digit `?store=`, so step 100+ silently rendered step 1, a hidden 99-store limit. It now accepts any safe integer; the view validates it against the draft.
  8. **Q2-O04 residual.** The account plan Actions column uses the approved C10 treatment: divider above on mobile (`border-t pt-5`), beside on desktop (`lg:border-l lg:pl-8`, 20 rem), 12 px gaps.
- **Unchanged:** database, RLS/RBAC, stored roles, live auth, Stripe, email, provisioning, vendors, dependencies; the real admin/superadmin gate (R-008/R-009); exact R-011 declaration, unchecked default, strict boolean validation, review summary, Me / Someone else; quote/consent rules; REPAIR_001 behaviour.
- **Affected ACs/files:** AC-05 and AC-06a wording extended (ACCEPTANCE_SPEC v1.2→v1.3; nothing removed); DATA_CONTRACT v1.3→v1.4 (§6 initial purchase, §10 binding); UI_SPEC C05/C06/C14 hold/closed states; internal `src/types/portal/state.ts` (`closedReason`; not the frozen view contract, so `portal-contract.ts` is unchanged); ACCEPTANCE_LEDGER; QAM engineering handoff §9.
